### 推荐替代方案

#### 方案 A: control-toolbox（推荐）
- **项目**: https://github.com/ros-controls/control_toolbox
- **许可**: BSD-3-Clause
- **优势**:
  - 经过 ROS 社区长期验证，用于实际机器人控制
  - 支持多种抗饱和策略（conditional integration, back-calculation）
  - 线程安全、实时友好
  - 支持 C++17/20
- **集成成本**: 中等（需要提取核心 PID 类，不依赖 ROS）
- **ARM 兼容**: ✅ 良好

#### 方案 B: simple-pid（轻量）
- **项目**: https://github.com/m-lundberg/simple-pid （Python 参考，需 C++ 实现）
- **备选**: 使用 Boost.Control 或自行实现（当前状态已接近成熟）

### 建议
**暂时保留当前实现**，原因：
1. 当前实现已针对电机电流控制场景优化（饱和周期计数、故障检测）
2. 实时性要求高，外部库引入风险较大
3. 代码量小（~78 行），维护成本可控
4. **改进方向**: 增加单元测试覆盖率，参考 control-toolbox 的抗饱和算法改进积分处理

## 2. 日志系统实现 ⚠️ 高优先级

### 当前实现
**位置**: `Atoms/ATOM-18_Diagnostics_Logging/`

**代码特征**:
```cpp
class LogWriter {
    std::deque<StoredEvent> queue_;           // 普通队列
    std::deque<StoredEvent> safety_queue_;    // 保底队列
    std::ofstream file_;
    std::thread thread_;
    // 手工实现：
    // - 异步写入线程
    // - 日志轮转（按文件大小）
    // - 队列满丢弃策略
    // - JSONL 格式序列化
};
```

**功能需求**:
- 异步非阻塞日志
- 分级日志（DEBUG/INFO/WARN/ERROR）
- 日志轮转（文件大小限制）
- JSONL 格式输出
- 双队列（普通 + 安全保底通道）
- 线程安全

### 推荐替代方案

#### 方案 A: spdlog（强烈推荐）
- **项目**: https://github.com/gabime/spdlog
- **许可**: MIT
- **版本**: 1.12+ （支持 C++17/20/23）
- **优势**:
  - **异步日志**: 内置异步模式，队列满时可配置丢弃策略
  - **日志轮转**: 支持按大小、时间轮转（`rotating_file_sink`）
  - **零开销**: Header-only 模式，编译期优化
  - **格式化**: 支持自定义格式器，可实现 JSONL 输出
  - **线程安全**: 经过大量工程验证
  - **ARM 优化**: 在嵌入式 Linux 上广泛使用
- **集成难度**: 低
- **性能**: 纳秒级延迟，适合实时系统

**代码示例**（替换当前实现）:
```cpp
#include <spdlog/spdlog.h>
#include <spdlog/async.h>
#include <spdlog/sinks/rotating_file_sink.h>

// 配置异步日志
spdlog::init_thread_pool(8192, 1);  // 队列 8192，1 个后台线程
auto file_sink = std::make_shared<spdlog::sinks::rotating_file_sink_mt>(
    "marshland.jsonl", 
    cfg.max_file_size_bytes,  // 轮转大小
    cfg.max_files             // 保留文件数
);

auto async_logger = std::make_shared<spdlog::async_logger>(
    "marshland", file_sink, 
    spdlog::thread_pool(),
    spdlog::async_overflow_policy::overrun_oldest  // 队列满丢弃最旧
);

// 保底队列可用第二个 logger + 立即刷新
auto safety_logger = /* 配置为同步刷新 */;
```

#### 方案 B: NanoLog
- **项目**: https://github.com/PlatformLab/NanoLog
- **优势**: 极低延迟（< 10 ns），但需要预编译
- **劣势**: 集成复杂度高，格式灵活性差

### 迁移评估
| 维度 | 当前实现 | spdlog | 迁移工作量 |
|------|---------|--------|----------|
| 代码量 | ~324 行 | ~50 行配置 | 中等 |
| 异步性能 | 未优化 | 高度优化 | ✅ 改进 |
| 日志轮转 | 手工实现 | 内置 | ✅ 简化 |
| 格式化 | 手工拼接 | 模板 + 自定义格式器 | 需适配 JSONL |
| 测试覆盖 | 部分 | 广泛 CI | ✅ 改进 |
| 维护负担 | 高 | 零 | ✅ 降低 |

### 建议
**强烈建议迁移至 spdlog**，原因：
1. 日志系统是基础设施，成熟库显著降低 Bug 风险
2. 当前实现的轮转、队列管理都是 spdlog 已解决的问题
3. **保底队列需求**: 用两个独立 logger 实现（一个异步丢弃，一个同步保底）
4. **JSONL 格式**: 实现自定义 `spdlog::formatter`（约 50 行代码）

**迁移路径**:
1. 第一阶段：并行运行（spdlog + 当前实现双写），验证功能等价
2. 第二阶段：逐步切换各模块到 spdlog
3. 第三阶段：移除旧实现

## 3. JSON 手工序列化器 ⚠️ 中优先级

### 当前实现
**位置**: `Atoms/ATOM-16_HTTP_Web/Inc/JsonCodec.hpp`

**代码特征**:
```cpp
class JsonWriter {
    std::string out_;
    std::uint32_t depth_first_[8]{};  // 手工管理逗号与嵌套
    
    JsonWriter& add(std::string_view key, std::string_view value);
    JsonWriter& beginObject(std::string_view key);
    JsonWriter& endObject();
    static void EscapeTo(std::string& out, std::string_view text);  // 手工转义
};
```

**功能**: 手工拼接 JSON 字符串，处理转义、逗号、嵌套

### 问题分析
1. **重复工作**: 项目已引入 `nlohmann/json`，但 ATOM-16 为避免依赖泄漏手写序列化器
2. **维护风险**: 字符串转义容易出错（Unicode、控制字符）
3. **性能**: 手工拼接未必比 nlohmann/json 的优化快

### 推荐方案

#### 直接使用 nlohmann/json（推荐）
**当前状态**: 项目已使用 `nlohmann/json` 进行解析（`JsonBody::Parse`）

**建议**:
```cpp
// 替换 JsonWriter
nlohmann::ordered_json response;
response["request_id"] = request_id;
response["ok"] = true;
response["error"]["code"] = "NONE";
return response.dump();  // 自动转义、格式化
```

**优势**:
- 统一代码风格（解析和序列化用同一库）
- 消除手工转义的 Bug 风险
- `nlohmann::json` 已高度优化（SIMD、内存池）
- 减少 ~270 行自研代码

**顾虑与解决**:
- **依赖泄漏**: 当前 `JsonCodec.hpp` 不暴露 nlohmann 类型，改用 pimpl 保持接口隔离
- **性能**: nlohmann/json 在响应式 Web 场景下性能足够（已被 httplib 内部使用）

#### 备选方案: simdjson
- **项目**: https://github.com/simdjson/simdjson
- **优势**: 极高解析性能（GB/s 级别）
- **劣势**: 主要优化解析，序列化不如 nlohmann/json 方便
- **适用场景**: 如果日后需要高吞吐解析大 JSON

### 建议
**中优先级迁移**: 用 `nlohmann::ordered_json` 替换 `JsonWriter`
- **时机**: ATOM-16 功能稳定后重构
- **收益**: 删除 ~270 行代码，统一 JSON 处理
- **风险**: 低（接口兼容性通过 pimpl 保证）

## 4. 线程池与任务调度 ⚠️ 中优先级

### 当前实现
**观察**: 多个 ATOM 模块手工管理线程

**示例**:
```cpp
// ATOM-17: WebSocket 推送线程
pthread_t push_thread_;
pthread_attr_t attr;
pthread_attr_setstacksize(&attr, kPushThreadStackBytes);
pthread_create(&tid, &attr, entry, arg);

// ATOM-18: 日志写线程
std::thread thread_;
thread_ = std::thread([this] { ThreadMain(); });

// ATOM-16: HTTP 服务线程
std::thread server_thread = std::thread([this]() {
    lowerThreadPriority();
    impl_->server.listen_after_bind();
});
```

**问题**:
1. 每个模块独立创建线程，资源浪费
2. 无统一的优先级管理
3. 缺少线程复用与任务队列

### 推荐方案

#### 方案 A: BS::thread_pool
- **项目**: https://github.com/bshoshany/thread-pool
- **许可**: MIT
- **特点**:
  - Header-only，单文件（~500 行）
  - C++17，轻量级
  - 支持任务优先级、等待、超时
- **适用**: 通用后台任务（日志、网络I/O）

#### 方案 B: Intel TBB
- **项目**: https://github.com/oneapi-src/oneTBB
- **许可**: Apache 2.0
- **特点**:
  - 工业级并行库
  - 任务窃取调度器
  - 丰富的并行算法
- **劣势**: 依赖较重，可能过度设计

### 建议
**中优先级**: 引入轻量级线程池（BS::thread_pool）
- **适用模块**: ATOM-18（日志）、ATOM-16（HTTP worker）
- **保留独立线程**: ATOM-17 推送线程（实时性要求高）
- **收益**: 减少线程数量，统一资源管理

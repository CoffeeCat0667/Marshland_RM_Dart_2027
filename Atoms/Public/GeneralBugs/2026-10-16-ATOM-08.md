## 1. 新增缺陷

### BUG-2026-10-16-08-01 — 命令入口无调用方（归属：顶层装配层 + ATOM-16 / ATOM-13 / ATOM-14）

**现象**：`Entry.cpp` 中对 `ChargeController` 的引用只有构造（`:471`）与适配器构造（`:522`）；`requestCharge` / `requestStopCharge` / `requestHome` **零调用**。

**影响**：WEB 手动（ATOM-16，已实现未接入）、自动流程（ATOM-13，无实现）、安全恢复（ATOM-14，已实现未接入）三条上行链路都没有把"动作"翻译成这三个调用 ⇒ ATOM-08 永远停在 `Idle`（即使此后补上 `tick` 调用方也无事可推进）。

**建议**：装配层为三条链路各写桥接（WEB 动作名 → `charge_start/stop/home`；ATOM-13 的四发流程步骤；ATOM-14 的恢复回零），并明确 `requester`（`WEB` / `AUTO`）与 `request_id` / `timestamp_us` 的填充规则。

### BUG-2026-10-16-08-02 — `StubChargeMotorCommandSink` 恒返回 false（归属：顶层装配层 + ATOM-05）

**现象**：`Entry.cpp:145-150`：`submitVelocityTarget` 打印后 `return false;  // Stub always fails until ATOM-05 command interface is ready`；`:152-155` 的 `clearVelocityTarget` 同样恒 `false`。

**影响**：ATOM-08 每次 `requestCharge` / `requestHome` 都会进入 `submitBothMotorsLocked` 的失败分支 → `enterFaultLocked(MotorCommandFailed)` → 状态 `Fault` + 上报 ⇒ **任何动作都无法启动**，且每次请求都会把模块推进故障态。

**说明**：`AllBugs` §6 的桩清单把该项记为"包装 `MotorCore`"，未记录"恒失败"；`ALL-05-01` 记的是根因（ATOM-05 缺"提交速度目标"能力），本条是该根因在本链路上的**具体后果**，建议在桩清单中显式标注。

### BUG-2026-10-16-08-03 — `StubLimitSwitchState` 恒"未就绪"（归属：ATOM-06 + 顶层装配层）

**现象**：`Entry.cpp:163-168`：`readChargeLimit` 恒 `return false` 且 `out.valid = false`。

**影响**：回零期间必然上报 `LimitInputInvalid`，25 s 后 `HomeTimeout` → `Fault`；双限位"均低"回零条件永远无法成立（与 `ALL-06-03`：ATOM-06 无实现同源）。

### BUG-2026-10-16-08-04 — ATOM-16 仍使用已删除的旧 SBUS/CAN 契约，导致 `marshland` 链接失败（归属：ATOM-16，Public 契约变更方）

**现象**（2026-10-16 实测，`cmake --build --target atom_16_http_web`）：

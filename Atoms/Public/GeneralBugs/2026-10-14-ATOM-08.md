## BUG-20261014-01 — 配置缺少 9 个 schema 已声明的域，且校验静默放行

**归属 ATOM**：`ATOM-15_Config_Persistence`（配置加载、校验与 schema 驱动）；受影响消费方：ATOM-05、ATOM-06、ATOM-07、ATOM-10、ATOM-11、ATOM-12、ATOM-16、ATOM-17、ATOM-18。

**现象**：`Rule/ConfigSchema.schema.json` 顶层 `properties` 声明了 20 个域，`Config/dart_control.json` 只提供了 12 个：

```text
schema 声明：schema_version, baseline, mode, timing, motor, motor_control, motor_encoder,
            charge, force, servo_mechanisms, can, sbus, gpio, servo, vision, http,
            websocket, persistence, fault, thread, log
config 实有：schema_version, baseline, mode, timing, motor, charge, force, can, sbus,
            servo, thread, persistence, reserved_001
缺失域（9）：motor_control, motor_encoder, servo_mechanisms, gpio, vision, http,
            websocket, fault, log
```

**为什么校验没拦住**：schema 顶层 `required` 只列了 `["schema_version","baseline","mode","timing","motor","charge","force","can","sbus","persistence","servo","thread"]`，上述 9 个域均不在 `required` 中。

**影响（按消费方）**：

| 缺失域 | 规则文档要求 | 受影响 ATOM |
|---|---|---|
| `motor_control` / `motor_encoder` | `ConfigSchema.md` §2.4.2 / §2.4.4（输出限幅、电流限幅、离线/反馈超时、异常值上限 7500 rpm 等） | ATOM-05 |
| `servo_mechanisms` | §2.6（换弹/供弹/发射舵机角度） | ATOM-07 / 10 / 11 |
| `gpio` | §2.9 | ATOM-06（见 BUG-02） |
| `vision` | §2.11 | ATOM-12 |
| `http` | §2.12，并明确"ATOM-16 只消费这些字段，**禁止**在代码中另行硬编码路由表或错误码表" | ATOM-16 |
| `websocket` | §2.13，同样禁止硬编码消息类型与 payload 字段 | ATOM-17 |
| `fault` | §2.15，并禁止新增 §14.2 之外的故障码 | ATOM-14 / 18（见 BUG-05） |
| `log` | §2.17 | ATOM-18 |

**归属判定**：配置内容缺失由配置维护方补；但"缺失却不报错"是 `ATOM-15` 的校验责任（`ConfigSchema.md` §4 第 3 条要求必需键缺失即失败），同时 `Rule/ConfigSchema.md` 的 `required` 约定与 schema 不一致也需修订。

**建议**：① 补齐 9 个域（或对确属可选的域在 `Rule/ConfigSchema.md` + schema 中显式声明为可选并说明缺失时的安全行为）；② `ATOM-15` 对"键存在但整段缺失"给出可定位的校验告警，不得静默通过。

## BUG-20261014-02 — `gpio` 段整体缺失，蓄力回零判据不可得（阻塞 ATOM-08 回零）

**归属 ATOM**：`ATOM-06_GPIO_Sensors`（限位/GPIO 配置的消费方与语义拥有方）；配置侧同 `ATOM-15`（见 BUG-01）。

**现象**：`Config/dart_control.json` 中不存在 `gpio` 段；全文件仅有一处相关键 `timing.gpio_sample_period_ms`。`ConfigSchema.md` §2.9 声明了 10 个 `gpio.*` 键，全部在 config 中缺失：

```text
gpio.limit_switch[]  gpio.sample_period_ms  gpio.default_level  gpio.active_level
gpio.charge_home_criterion  gpio.debounce_ms  gpio.report_on_change
gpio.report_max_delay_ms  gpio.read_failure_handling  gpio.limit_trigger_action
```

**影响**：
- **ATOM-06**：采样周期、去抖、有效电平、限位↔电机映射、回零判据、读取失败处理、限位触发动作全部无配置来源；按 `Rule/AtomIntegration.md` §5 与 `ConfigSchema.md` §1.7，禁止用臆造默认值顶替，只能如实失败。
- **ATOM-08**：**不受阻塞**。2026-10-14 用户裁决采用选项 A——ATOM-08 不读取 `gpio.*`，只调用窄端口 `ILimitSwitchState`（"双限位是否同时有效且稳定为低"），判据细节归 ATOM-06。
- 该缺口的处置：用户已决定本阶段不补 `gpio` 段，本条保留为 ATOM-06 的实现/联调前置条件。

**建议**：补 `gpio` 段（`Design/Config.md` §8.1 已给出全部数值）；`limit_switch[].pin` 按既定裁决保持 `null`（本版本不接入物理通道）。

## BUG-20261014-03 — `sbus.rules[]` 缺失，控制源选择无表可依

**归属 ATOM**：`ATOM-02_State_Arbitration`（`SelectControlSource` 实现方）；配置侧 `ATOM-15`。

**现象**：`Config/dart_control.json` 的 `sbus` 段有 20 个键，但**没有 `rules`**；而：
- `Rule/ConfigSchema.md` §2.8.2 明确"**规则表必须入 JSON**"，并要求逐条给出 `id` / `when` / `then_source` / `never_changes_fire_priority`；
- `Design/Config.md` §7.2 定义了 6 条规则（`startup_no_web`、`web_connected`、`sbus_online_auto_mode_true`、`sbus_online_auto_mode_false`、`sbus_lost`、`software_estop`）；
- schema 中 `sbus.required` 只有 `["serial_device","channel_scale_x"]`，因此缺失不会被校验拦截。

**影响**：控制源（`AUTO`/`WEB`/`SBUS`/急停覆盖）无法按配置表求值；按 `ConfigSchema.md` §2.8.2 又"**禁止**在代码中另行硬编码条件分支"，导致该判定缺少合法实现依据。ATOM-08 的"先确定控制权归属"链路（决定读取 CH2/CH8/CH9 还是 WEB/AUTO 目标）因此无法闭环。

**建议**：补 `sbus.rules[]` 六条，或将该判定明确移出配置表并同步修订 `ConfigSchema.md` §2.8.2 与 `Design/Config.md` §7.2。

## BUG-20261014-04 — `sbus.functions[]` 缺少文档要求以 `null` 出现的映射项

**归属 ATOM**：`ATOM-03_SBUS`（`sbus.functions[]` 的消费方与"未映射"语义拥有方）；配置侧 `ATOM-15`。

**现象**：config 的 `sbus.functions[]` 现有 8 项（`auto_mode`、`estop_trigger`、`manual_charge`、`manual_charge_left`、`manual_charge_right`、`manual_reload`、`manual_yaw`、`manual_fire`）。而 `Rule/ConfigSchema.md` §2.8.1 写明：

> **`[待定]` 通道必须写为 `null`**（当前：`sbus.estop_confirm`、`sbus.auto_start` 的通道待定）。`ATOM-03` 遇到 `null` 时**必须**保持该功能未映射，**禁止**推断。

即 `estop_confirm`、`auto_start` 应以 `"channel": null` 的形式存在；现在两项**完全缺失**，消费方无法区分"该功能已声明但通道待定"与"该键不存在"。

**建议**：补两条 `{"name":"estop_confirm","channel":null,"signal_type":"SWITCH"}`、`{"name":"auto_start","channel":null,"signal_type":"SWITCH"}`（`signal_type` 取值请按 `Design/Config.md` §7.1 确认）；`manual_mode_toggle`、`stop_fire`、`manual_feed`、`manual_force` 是否需要入表，请一并裁决。

## BUG-20261014-05 — `fault` 段缺失，故障表与安全规则无配置来源

**归属 ATOM**：`ATOM-14_Safety_Recovery`（故障与恢复编排）、`ATOM-18_Diagnostics_Logging`（故障记录与诊断）；配置侧 `ATOM-15`。

## BUG-20261014-06 — 故障表缺少"蓄力超时/回零超时"条目

**归属 ATOM**：`ATOM-14_Safety_Recovery`（故障表消费与恢复编排）；设计侧 `Design/Config.md` §14.2。

**现象**：`Design/Atomic/ATOM-08_Charge.md` 内部原子操作第 11 条要求"将蓄力超时、电机或限位错误报告给 ATOM-14"，`Design/Config.md` §4 也定义了"蓄力最大动作时间（超时进入故障处理）"；但 §14.2 故障表中**没有**蓄力超时/回零超时对应的故障码与等级，而 `Rule/ConfigSchema.md` §2.15 又禁止新增表外故障码。

**影响**：ATOM-08 只能上报自定义类别（`ChargeTimeout` / `HomeTimeout` / `MotorCommandFailed` / `LimitInputInvalid` / `ConfigReloadFailed`），无法给出合法故障码；装配层与 ATOM-14 也没有配置依据可查。

**建议**：在 `Design/Config.md` §14.2 增补蓄力/回零超时条目（含等级、自动恢复与人工确认条件），或明确归类到既有故障码；同步 `Rule/ConfigSchema.md` §2.15 与 `Config/dart_control.json` 的 `fault.table`。

## BUG-20261014-07 — 顶层编译命令未启用 `-Wall -Wextra -Wpedantic`

**归属**：**顶层 CMake / 工程**（非某个 ATOM）；规则依据 `Rule/AtomIntegration.md` §9.3。

**现象**：`cmake-build-ubuntu-arm/compile_commands.json` 中 ATOM-08 各源文件的编译命令为

```text
/usr/bin/aarch64-linux-gnu-g++ -I... -g -std=c++23 -fdiagnostics-color=always -o ... -c ...
```

不含 `-Wall` / `-Wextra` / `-Wpedantic`。

**影响**：§9.3"必须在 `-Wall -Wextra -Wpedantic` 下零警告"无法由常规 `cmake --build` 路径校验，各模块只能各自补验（本轮 ATOM-08 以独立严格编译补验：3 个源文件零警告）。

**建议**：在顶层 CMake 对所有模块统一追加这三个警告选项（`add_compile_options` 或对公共聚合目标 `target_compile_options`），使规范由构建链路强制。

## BUG-20261014-08 — 限位接口缺少"与运动方向冲突"语义，F-LIMIT-001 无法在消费方实现

**归属 ATOM**：`ATOM-06_GPIO_Sensors`（限位检测与语义拥有方）、`ATOM-14_Safety_Recovery`（故障条目与恢复编排）。

**现象**：`Design/Config.md` §14.2 定义 `F-LIMIT-001`「非回零动作期间触发与当前运动方向冲突的限位」→「停止相关电机」；但现有公共接口只提供"某个限位的稳定电平/有效性"这一层信息。ATOM-08 使用的窄端口 `ILimitSwitchState::readChargeLimit(motor_id, sample)` 只能给出 `valid` / `low`，**拿不到限位所在物理端点与"方向冲突"判据**；而 2026-10-14 的选项 A 裁决又明确 ATOM-08 **不读取** `gpio.*`（含 `gpio.limit_switch[].motor_id`、`gpio.active_level`）。

**影响**：ATOM-08 无法自行判定"普通蓄力期间限位触发且与运动方向冲突"，也就无法实现 F-LIMIT-001 的"停止相关电机"。若 ATOM-06 / ATOM-14 亦不实现，该故障条目即形成**职责空隙**（电机不会因限位冲突而停止）。

**当前缓解**：ATOM-08 已在 `tick` 中对"故障已激活且不处于 RECOVERY 阶段"的情形撤销蓄力/回零出力（2026-10-14 自审修复 D-3）。因此只要 ATOM-06 检出并上报 F-LIMIT-001，ATOM-08 会停止出力。

**建议**：明确 F-LIMIT-001 的检测归属；若归 ATOM-06，请在其窄端口/事件中补充"限位对应的运动方向约束"（或直接给出故障事实），并同步 `Design/Interface.md` §11.1 的"限位开关模块只负责采样、去抖和状态输出，不直接决定机构动作"。

## BUG-20261014-09 — ATOM-08 的 `tick()` 无周期调用方（动作只启动不收敛）

**归属 ATOM**：**顶层装配层**（非某个 ATOM 的代码缺陷）；规则缺口在 `Rule/AtomIntegration.md` §3.1(b)——"外部 update/tick"的**调用方**始终未裁决。

**现象**：ATOM-08 按裁决不创建线程，且 `RuntimeStep` 中没有对应步骤；在 `Atoms/` 全量检索 `tick(` 只命中 ATOM-08 自身的声明/定义与文档，`Atoms/Public` 层不存在 tick / 控制周期宿主（ATOM-05 的 `MotorCore::tick()` 由它自己的线程调用，不能替代）。

**影响（致命）**：`requestCharge()` 提交恒速目标后，X 秒完成判定、蓄力超时、双限位回零判定、回零超时、急停/故障撤销**全部不会发生** → 电机保持恒速目标，直到安全链路介入。

**建议**：顶层装配层明确"谁在 20 ms 控制周期调用 `ChargeController::tick(monotonic.nowMicros())`"，并保证 `ChargeController` 与全部被注入对象的寿命长于调用方；若决定新增或复用 `RuntimeStep` 承载，须先修订 `Rule/AtomIntegration.md` §3.1 与 `Design/Interface.md`。

## BUG-20261014-10 — `IMotorCommandSink::clearVelocityTarget` 映射语义未定义

**归属 ATOM**：**顶层装配层**（适配器映射）+ **设计裁决**（`Design/Config.md` 未定义蓄力"结束"的输出形态）；接口本身定义在 ATOM-08 的 `charge_interfaces.hpp`。

**现象**：ATOM-08 在"正常完成 X 秒蓄力""普通停止""急停/故障撤销"三种场景调用**同一个** `clearVelocityTarget()`。规范只写"X 秒到期后结束正常蓄力"，未说明是 **0 rpm 闭环保持**还是**零力矩**；而换弹机构（`Design/Config.md` §5.6）明确区分两者（动作完成后 0 rpm 保持 / 手动停止与急停零力矩）。

**影响**：若装配层把它映射成零力矩，则**蓄力完成瞬间机构失去保持力矩**，可能与设计意图不符。

**建议**：裁决并拆分接口（例如 `holdZeroVelocityTarget(motor_id)` 与 `dropToZeroTorque(motor_id)`），由 ATOM-08 在"完成/停止"与"急停/故障撤销"两条路径分别调用；改动局限在 ATOM-08 内部，成本低。

## BUG-20261014-11 — 故障上报端口只有"激活"语义，无法表达"仅记录"

**归属 ATOM**：**顶层装配层**（映射）+ **ATOM-14**（故障状态与恢复编排）；契约在 `Atoms/Public/AppInterfaces.hpp` 的 `IInputReporter::ReportFault(bool active, FaultSeverity)`。

**现象**：ATOM-08 的窄端口 `IFaultReporter::reportChargeFault(code, severity)` 需由装配层委托到 `ReportFault`，但该 Public 端口只有"激活 + 严重度"，没有"仅记录、不置故障"的通道。因此 ATOM-08 的 `ConfigReloadFailed`（热加载失败、按设计保留上一份有效配置）这类"记录型"事件会被映射成全局故障激活。

**影响**：轻则误报故障；重则使 ATOM-08 的 `tick` 因 `SystemMode` 转 `FAULT` 而中断正在进行的蓄力/回零。

**建议**：明确允许升级为全局故障的 `ChargeFaultCode` 白名单（建议仅 `ChargeTimeout` / `HomeTimeout` / `MotorCommandFailed` / `LimitInputInvalid`），其余走诊断/日志通道（ATOM-18）；或为"仅记录"补充公共诊断端口。

## BUG-20261014-12 — ATOM-08 生命周期适配器的注册步骤必须晚于配置加载

**归属 ATOM**：**顶层装配层**（注册步骤选择）；ATOM-08 侧已提供 ATOM 内注册接口。

**现象**：`LifecycleAdapter::initialize()` 直接经 `IConfigView` 读取 `timing.charge_*` / `charge.*` / `motor[]` / `sbus.functions[]`；`RuntimeStep` 中没有 ATOM-08 的专用步骤（`Rule/AtomIntegration.md` §3）。若装配层把它注册在 `LoadConfiguration` / `ValidateConfiguration` 之前，查询返回 `NOT_LOADED`。

**影响**：初始化如实失败（`success = false`）；当 `required = true` 时会导致整机 `INIT_FAILED`。

**建议**：注册到"晚于配置校验"的步骤（例如 `LoadPidParameters` 及之后）；或改为在配置模块就绪后于构造期直接调用 `ChargeController::configure()`，不依赖 `RuntimeStep`。

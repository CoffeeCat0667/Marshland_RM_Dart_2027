## 1. 问题摘要

在尝试将 ATOM-08/09/10/11 集成到 `Entry.cpp` 时，发现这 4 个模块的**构造函数签名**与当前启动架构存在**不可调和的循环依赖**：

- **这些模块的构造函数需要 `IControlAuthority` 和 `IStateReader` 接口**
- **这些接口由 `AppCoordinator` 提供**
- **但 `AppCoordinator` 必须在所有生命周期模块注册完成后才能构造**
- **生命周期模块注册需要先构造这些模块的内核对象**

这形成了一个**死锁**：模块构造 → 需要 AppCoordinator → AppCoordinator 需要模块先注册 → 注册需要模块先构造。

    runtime.addModule({RuntimeStep::LoadPidParameters, ...});
    // ... 更多注册
    
    // 4. 创建 AppCoordinator（此时所有生命周期模块已注册）

- `AppCoordinator` 构造函数需要 `RuntimeCoordinator&`，而 `RuntimeCoordinator` 需要先完成所有模块注册
- 因此 `AppCoordinator` 只能在步骤 4 创建，不能提前到步骤 2

## 4. 根本原因分析

### 4.1 架构假设冲突

**ATOM-08/09/10/11 的设计假设**：
- 这些模块是**业务逻辑层**，需要在运行时查询控制权、安全状态和系统模式
- 因此它们的接口设计为"在构造时注入 `IControlAuthority` 和 `IStateReader` 依赖"
- 这符合**依赖注入（DI）**最佳实践

**Entry.cpp 启动架构的假设**：
- `AppCoordinator` 是整个系统的"指挥官"，在所有子系统就绪后才创建
- 生命周期模块必须在 `AppCoordinator` 之前注册到 `RuntimeCoordinator`
- 这符合**分层启动（Phased Initialization）**最佳实践

**冲突点**：两个正确的设计原则在当前实现中产生了**时序矛盾**。

### 4.2 为什么 ATOM-03/04/05/07 没有这个问题？

这些模块是**硬件/服务层**：
- ATOM-03 (SBUS): 只负责读取 UART 数据，解码 SBUS 帧
- ATOM-04 (CAN): 只负责 CAN 总线收发
- ATOM-05 (Motor): 只负责 PID 计算，不判断是否允许执行
- ATOM-07 (Servo): 只负责 IIC 通信，不判断控制权

它们**不需要知道当前是谁在控制、是否急停、是否有故障**，因此不需要 `IControlAuthority` 和 `IStateReader`。

而 ATOM-08/09/10/11 是**机构控制层**：
- 需要判断"当前是 SBUS 控制还是 WEB 控制"
- 需要检查"是否允许执行蓄力/变力/换弹/发射动作"
- 需要读取"当前系统模式和安全状态"

因此它们**必须**依赖 `AppCoordinator` 提供的接口。

## 5. 可能的解决方案（需架构决策）

### 方案 A：延迟构造（推荐，影响最小）

**思路**：将 ATOM-08/09/10/11 的内核对象构造延迟到 `AppCoordinator` 之后。

**修改点**：
1. 生命周期适配器改为持有"内核对象的工厂函数"而非直接持有内核引用
2. `initialize()` 时才调用工厂函数构造内核对象（此时 AppCoordinator 已可用）

**示例**（伪代码）：

```cpp
// 当前（有问题）
ChargeController charge_controller(config, clock, ..., app);  // ❌ app 还不存在
auto adapter = std::make_unique<LifecycleAdapter>(charge_controller, config);
runtime.addModule({...});

// 修改后（方案 A）
auto charge_factory = [&]() {
    return std::make_unique<ChargeController>(config, clock, ..., app);
};
auto adapter = std::make_unique<LifecycleAdapter>(charge_factory, config);
runtime.addModule({...});

// ... 后续
AppCoordinator app{runtime, arbitrator, clock};  // ✅ 此时创建 app
app.Start();  // LifecycleAdapter::initialize() 内部调用 charge_factory() 构造内核
```

**优点**：
- 不修改 ATOM 模块代码
- 符合现有启动架构
- 对其他模块无影响

**缺点**：
- 需要修改 4 个 LifecycleAdapter 实现（ATOM-08/09/10/11）
- 增加了一定复杂度

---

### 方案 B：提前创建 AppCoordinator（不推荐，架构冲击大）

**思路**：在模块注册之前就创建 `AppCoordinator`。

**修改点**：
1. `AppCoordinator` 构造函数不再要求 `RuntimeCoordinator` 已完成注册
2. `AppCoordinator::Start()` 才触发 `RuntimeCoordinator` 的启动流程

**问题**：
- 违反了 `RuntimeCoordinator` 的设计原则（生命周期管理器应先注册再启动）
- 需要大幅重构 `AppCoordinator` 和 `RuntimeCoordinator` 的职责边界
- 影响所有已接入模块

**结论**：**不推荐此方案**。

---

### 方案 C：Setter 注入（折中方案）

**思路**：构造时不传 `IControlAuthority` 和 `IStateReader`，改为通过 setter 方法在运行时注入。

**修改点**：
1. ATOM-08/09/10/11 的构造函数移除这两个参数
2. 增加 `setControlAuthority()` 和 `setStateReader()` 方法
3. `AppCoordinator::Start()` 之后调用这些 setter

**示例**（伪代码）：

```cpp
// 构造时不传（或传 nullptr）
ChargeController charge_controller(config, clock, ..., nullptr, nullptr);
runtime.addModule({...});

AppCoordinator app{runtime, arbitrator, clock};

// 启动后注入
charge_controller.setControlAuthority(&app);
charge_controller.setStateReader(&app);

app.Start();
```

**优点**：
- 最小化对启动架构的改动

**缺点**：
- **需要修改 ATOM 模块代码**（违反了"不修改 ATOM 代码"的约束）
- 存在"对象部分初始化"的风险期（setter 调用之前）
- 不符合 C++ 依赖注入的最佳实践

---

### 方案 D：AppCoordinator 前置接口代理（待评估）

**思路**：创建一个"未就绪的 IControlAuthority/IStateReader 代理"，构造时传入，运行时替换为真实的 `AppCoordinator`。

**修改点**：
1. 创建 `AppCoordinatorProxy` 类，实现 `IControlAuthority` 和 `IStateReader`
2. 构造时传入 proxy
3. `AppCoordinator::Start()` 后，proxy 内部指向真实的 `AppCoordinator`

**问题**：
- 引入了额外的间接层
- proxy 在 `AppCoordinator` 就绪前被调用时如何处理？（返回默认值？抛异常？）

**结论**：需要更详细的设计才能评估可行性。

## 9. 结论

**核心矛盾**：
- ATOM-08/09/10/11 的构造需要 `AppCoordinator`
- `AppCoordinator` 的构造需要先完成所有模块注册
- 模块注册需要先构造模块内核对象
- **形成循环依赖死锁**

**根本原因**：
- 业务逻辑层模块（ATOM-08/09/10/11）首次引入了对"系统级协调器"的依赖
- 现有启动架构未预见到这种依赖模式

**不能通过简单的代码调整解决**：
- 不修改 ATOM 模块代码的前提下，无法在 Entry.cpp 层面解决
- 需要架构层面的决策和设计调整

**建议**：
- 采用**方案 A（延迟构造）**，影响最小且符合现有架构原则
- 需要修改 4 个 LifecycleAdapter 的实现，增加工厂函数支持

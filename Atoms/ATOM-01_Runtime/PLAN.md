# ATOM-01_Runtime 实现方案（初稿）

> 编制日期：2026-09-27
> 依据：`AGENTS.md` 与 `Design/Atomic/ATOM-01_Runtime.md`

## 1. 目标与边界

实现 Marshland 的进程生命周期与启动协调模块：按安全顺序执行模块初始化，汇总初始化结果，在全部必需模块成功时进入 `STANDBY`，任一必需模块失败时进入 `INIT_FAILED`，并在关闭时按已启动模块逐项停止和释放资源。

本模块不实现发射流程、机构动作或具体硬件驱动；不定义 `main()`。具体设备参数和安全配置来自配置文档，不在本模块内补造待定数值。

## 2. 初步目录与构建方案

- `Inc/`：公开接口和数据类型头文件。
- `Src/`：生命周期协调器及其内部实现。
- `CMakeLists.txt`：定义 `atom01_runtime` 模块目标，采用 `INTERFACE` 目标作为当前无实现源码阶段的模块化占位；编译器、平台、C++ 标准和编译选项由上层工程统一决定。
- 不创建独立可执行文件，不创建测试入口 `main()`。

## 3. 建议的核心抽象

1. **生命周期状态**：至少覆盖启动中、`STANDBY`、`INIT_FAILED`、关闭中/已关闭等状态。
2. **初始化步骤结果**：每个步骤独立返回成功/失败、模块名、错误原因和是否为必需项，支持逐步诊断。
3. **模块生命周期接口**：为日志/诊断、配置、PID、SocketCAN、电机/编码器、GPIO/限位、IIC/PCA9685A、舵机、SBUS/视觉、HTTP/WebSocket 等模块提供统一的初始化与停止调用边界。
4. **启动协调器**：按设计文档列出的顺序逐项调用，不把多个模块副作用隐藏在不可分割的单一操作中。
5. **安全门控**：未完成初始化或进入 `INIT_FAILED` 时拒绝自动发射及普通手动执行器动作，并把模块名和错误原因暴露给状态/诊断接口。
6. **关闭流程**：只对已成功启动的模块执行逆序或约定顺序的停止/释放，并保证每个已启动模块都收到释放调用。

## 4. 实现阶段计划

### 阶段 A：接口与状态模型

- 明确状态、错误、步骤结果和生命周期上下文的数据结构。
- 设计模块适配接口，避免在 ATOM-01 中耦合具体硬件实现。
- 确定配置读取接口与必需/可选配置项校验边界。

### 阶段 B：启动协调

- 实现配置加载、解析和必需项校验。
- 按既定顺序执行各初始化步骤。
- 每一步记录结果；必需步骤失败立即进入 `INIT_FAILED` 并触发安全禁止。
- 所有必需模块成功后切换至 `STANDBY`。

### 阶段 C：关闭与诊断

- 实现关闭事件处理和已启动模块的停止/资源释放。
- 保留失败步骤及模块错误原因，供状态/诊断接口查询。
- 确保重复关闭、部分启动失败等边界场景不会重复释放或继续执行动作。

### 阶段 D：验证

- 为每个初始化步骤分别覆盖成功和失败路径。
- 验证任一必需模块失败时状态为 `INIT_FAILED` 且动作请求被拒绝。
- 验证全部必需模块成功时状态为 `STANDBY`。
- 验证关闭时每个已启动模块均收到停止/释放调用。
- 验证模块不包含 `main()`，并能被上层 CMake 作为子目录组织和链接。

### 5.1 与业务状态机的关系（`ATOM01-BUG-010` 结论）

本模块**不驱动**业务 `SystemMode`，也不持有 `StateArbitrator`：

- `RuntimeState`（含 `Standby`）只表示"硬件与服务是否已拉起"，是 ATOM-01 私有的生命周期细分，**不等于** `SystemMode::STANDBY`。
- 启动结果到业务模式的映射、以及"启动前推进 `INITIALIZING`"，统一由装配层 `Atoms/Public/AppCoordinator` 在调用 `start()` 之前/之后完成（`UNINITIALIZED -> INITIALIZING -> STANDBY / INIT_FAILED`）。
- 因此**不**在 `start()` 内新增"开始初始化"通知回调：那会使状态驱动源分裂为两处，形成与状态机并存的"第二真相"。

依赖方向保持 `Atom -> Public`，本模块不反向依赖 ATOM-02 或 AppCoordinator。
